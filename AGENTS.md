## Primary melee — attack action (not collision damage)

Sword **colliders must not** be the source of HP damage (use them for VFX / clash / debug only). Real damage comes only from a **server-authoritative** phased attack on **`PlayerCombat`**:

**Owner → host timing:** The attack pattern is **windup → charge → active → recovery**, and the numbers come from the equipped item's **weapon class**. The designer home is the **`MeleeWeaponTimingLibrary` component in the INSPECTOR** (on the scene NetworkManager, next to CombatAuthority) — rows resolve live, so play-mode edits hit the next swing; `Assets/data/melee_weapon_classes.json` is only the fallback for scenes without the component, then built-ins. Class selection: `equipment_profiles.json` `weaponClass` + optional `meleeOverrides`; `PlayerCombat.FallbackWeaponClass` covers bare hands / entities / dummies — see `PlayerCombat.GetMeleeWeaponTimings`. **Windup elapses while the button is held**: release sends intent immediately, and the host plays only the **remaining** windup (`max(0, windupSeconds − hold)`) before the active sweep — a long hold releases straight into damage, a quick click still lifts the sword first. Then **outcome combat recovery**. **The swing basis (yaw + pitch) is pinned from the intent at commit for every pawn, local owner included** (`PushMeleeAttackBasisFromIntent`) — turning the camera mid-swing does not drag the arc, and the painted fan / damage share one fixed basis (this is what makes fan seams impossible; do not reintroduce a live-camera basis mid-swing).

1. **Attack selection** — directional cursor locks on press (`SouthpawSwing` inverts L/R attack **type** only). **Attack teardrop (HUD):** screen-left teardrop = **right** swing / right-side attack path; screen-right = **left** attack. **Block teardrop:** screen-left = left hold (same side as guard). Mouse evidence for attacks uses mirrored L/R cardinals vs block.
2. **Light / heavy timing** — heavy = hold ≥ effective **windup + charge** (initiative armed swaps in `initiativeWindupSeconds`; oneHanded 0.2 + 0.2 = **0.4 s**, or 0.1 + 0.2 with initiative). One-handed sheet values: windup **0.2s** (initiative **0.1s**) + active **0.25s** + outcome recovery (miss **0.3** / hit **0.2** / blocked **0.2** / parried **0.4**, applied after return frames). Heavy adds `MeleeHeavyAttackDamageBonus` (+0.3) to the combat multiplier and uses a slower anim playback (`MeleeHeavySwingPlaybackRate`). **Damage** = `round(MeleeWeaponBaseDamage × multiplier)` — one flat active window. `combo*` class fields are STAGED data (nothing reads them until light combos are implemented); `special*` fields are live — see the special attack below.
3. **Geometry** — `MeleeAttackPath` in combat-local space (+X forward, +Y up, +Z right). L/R: horizontal arc; overhead: vertical XY arc. Reach comes from class **meters** (`reachForwardMeters` / `reachLateralMeters`) converted once per pawn via `PlayerCombat.GetMeleeAttackRangeUnits` (BodyHeight/1.8).
4. **Initiative** — a clean hit (not blocked/parried) arms initiative on the host for `InitiativeWindowSeconds` (**2 s**). Its reward is data-driven per class: the shorter `recoveryHitSeconds` (vs miss) on that swing, and `initiativeWindupSeconds` instead of `windupSeconds` on the **next** attack (one follow-up consumes it; blocked/parried clears it). No multiplier — the sheet values are explicit seconds.
5. **Hits** — `MeleeAttackSweep` sphere substeps along tip+heel motion (`MeleeHitVolumeThickness`). Per-target dedup; optional multi-hit via `MeleeAllowMultipleHitsPerAttack`.
6. **Attack path** — `MeleeAttackArcDegreeStep` (default 1°) samples the swing along `MeleeAttackPath` (~150 samples on a 150° arc, 360 on a full turn). Colored overlay lines are optional (`MeleeDebugDrawEnabled`); the path sampling is core combat readability. **Arcs are bound to the swing clip:** a peer only draws active-sweep lines while `PlayerAnimation.HasActiveMeleeSwingPresentation` is true on that machine — never an arc without an animation. Damage sweeps are unaffected (authority never depends on presentation).
7. **`CombatAuthority`** validates intent, rate limits, stamina, then calls `PlayerCombat.ServerStartMeleeAttackAction`.
8. **Attack commitment lock** — from **Attack1 press** (owner preview) through host windup + swing: ground move at **`MeleeAttackMoveSpeedScale`** (default **10%**); sprint suppressed; airborne velocity kept. Look uses slowed mouse + yaw/pitch cone via `OnEyeAngles`. **Windup telegraph:** black (light) / white (heavy) on press/hold and during host windup; the **yellow active path overlay** only after release during the damage window. Dummy black telegraph flash length = class windup (`GetMeleeWindupSeconds`). **Press anim:** `BeginMeleeAttackWindupHold` starts the attack clip **once**; hold freezes a windup pose (`PlaybackRate=0`); release resumes that same clip by restoring the playback rate. Release must **not** re-pulse `b_attack` when the press already started a clip — that restarted it from frame 0 and read as a stutter as the swing began.
9. **Combat recovery** — soft miss/hit: lock = **remaining swing presentation window + short buffer** (~0.1s); **no interrupting pistol sequence**. Hard recoveries: shove punch still uses a sequence; **victim/blocker fall uses stagger `IsGrounded=false` only** (never `UseAnimGraph=false` flail — that froze clients). Chain-busy = host sweep + recovery/stagger lock + **swing presentation remaining** (next attack waits for the clip to finish). `AttackCooldownAfterRelease` default **0**.
   **One swing at a time, one queued follow-up:** pressing Attack1 while chain-busy queues **exactly one** light attack (`QueuedAttackMaxAgeSeconds`, default 0.75 s — a stale click expires; block/shove/hit-reaction clears the queue) that fires the moment the chain frees. **Held starts:** both combat channels allow a HELD button to begin the action the first frame cooldown/recovery opens (`CombatChannel.Step allowHeldStart`) — holding attack through recovery starts the next windup immediately; holding block through its cooldown re-guards immediately (a consumed/broken block still requires an actual release first). Still no auto-start from a held button and no multi-press buffer; `PlayerAnimation.IsMeleeSwingAnimBusy` (time-bounded presentation window) remains the single gate, and clearing a recovery sequence must preserve a running swing clip (`ExitCombatSequenceToLocomotion` skips the `b_attack` reset while a swing is presenting — resetting it produced arcs with no animation).
10. **Hit reaction (victim)** — `PlayerAnimation.HitReaction.cs` is the **only** "I was just hit" state, and it lives on **animation, not combat**, so the window and the pose have one owner that always ticks. **Resolve victims by `PlayerAnimation`** (shove trace, `ApplyMeleeStaggerToVictim`) — being hit is not equipment-dependent; `PlayerCombat` only exposes `IsHitReactionActive` for `IsCombatActionLocked` and `OnHitReactionBegan()` to drop its own in-flight state. Host picks a duration (`HitReactionSeconds` default **0.9 s**, or the caller's value — shove victim 1.2 s, shove-vs-block 0.5 s, heavy block 0.4 s) and `[Rpc.Broadcast]` gives every machine the same local deadline. Pose is the **looping flail sequence** `airborne_flail_movement` with `UseAnimGraph=false` (re-asserted from `PlayerAnimation.OnUpdate`, restarted only on the first frame) and the **held sword is destroyed for the whole window** (`TickHoldPose` / `TickMeleeDemoStickTransform` refuse to re-create it); the window end **hard-restores** locomotion and the hold pose once. `PlayerAnimation.TickHitReactionPose` owns **both** the pose and its exit and runs from `OnUpdate` **and `OnPreRender`** — a pawn's `OnUpdate` is skipped on peers where it is a proxy, so an exit that lived only in `PlayerCombat.TickHitReactionState` let that peer loop the flail forever. `HitReactionMaxSeconds` (2.5 s) caps any caller. Do **not** go back to an animgraph-only pose (`b_grounded=false`): `PlayerController` rewrites grounded state every frame on whichever machine simulates the pawn, so only proxies (the host's view of a client) played the reaction — a sequence is the same on every peer. During it: no attack/block/shove (`IsCombatActionLocked`), **no jump** (cleared in `PlayerMovement.PreInput`), and the **grapple detaches and cannot re-attach**. Do **not** re-add authority/proxy gates to this tick — the old stagger path had four gated tick sites and the host never expired client-owned pawns, which froze them in the fall pose and locked them out of combat. `MeleeStaggerTier` survives only as **block JSON data**, and `AirborneFlail` is gone.
11. **Shove (F)** — a **player ability, not a weapon one**: it works bare-handed and will become an unlockable augment (see Augment Station / `PlayerAugments`). `PlayerEquipment` must **never** disable `PlayerCombat` to express "no weapon" (that killed the shove, the hit reaction, and the jump/grapple locks at once) — the sword gate is the `PlayerEquippedItem.HasAction( PrimaryMelee )` check inside `PlayerCombat.OnUpdate`, which `TickOwnerShoveInput()` deliberately runs **before**, plus `RejectNoMeleeItemEquipped` on the host in `CombatAuthority`. Hand harvest / gather is **E** (`HandHarvest`); shove stays on **F** (`Shove`). Anytime **grounded**: spends **`ShoveStaminaCost`** (default **10**), dashes **`ShoveDashMeters`** (default **1 m**, converted via BodyHeight/1.8 ≈ **40** pawn units) flat-forward, then punch hit. Attacker then enters **`RecoveryShoveCombatLockSeconds`** (default **0.8 s**, extended to cover the punch clip) via `IsCombatActionLocked` (blocks sword, block, shove, and sprint; Attack1 during kick is not buffered into a swing). Owner gets lock via Rpc.Owner + local prediction. Vs block → blocker **stagger** **0.5s**; vs open → 3 damage + victim **stagger fall** **`RecoveryDefenderShoveSeconds`** (default **1.2s**).
12. **Facing & camera (Valheim-style)** — third person with **no attack/block held**: orbiting the camera does **not** turn the body (`PlayerMovement.FreeLookOrbitEnabled` runtime-drives `PlayerController.RotationAngleLimit` to 180°; prefab value restored while Attack1/Attack2 are held or in first person — a blocker must physically turn with the camera; moving still aligns the body to travel, which is the intended Valheim walk-facing). **Combat facing is presentation, not physics**: never fight the pawn ROOT for facing — the stock controller + rigidbody interpolation re-align it to movement every frame, and root writes visibly spazz. Instead `PlayerCombat.TryGetCombatFacingYaw` is pure data (priority: in-flight swing basis → broadcast windup telegraph → authoritative block guard → local attack/bow hold → shove window) and `PlayerAnimation.TickCombatFacingPresentation` applies it to the **Body renderer child only**, from OnUpdate + OnPreRender so it lands last before render on every peer with facing data. On release the override is dropped with **NO rotation writes**: the body stays exactly where the swing pinned it and the PlayerController takes over from that pose (lingers while standing, turns toward locomotion once moving). Never blend the body toward "root facing" or reset its LocalRotation to identity on release — **the physics root never rotates in this project (it keeps its spawn yaw forever)**, so root-relative resets turn the model toward the SPAWN direction after every swing (shipped twice before this was understood). **Combat writes NOTHING to the pawn root or the camera — ever.** Any root write on a combat action moves the player's view (the controller couples them internally); that class of bug came back twice before this rule was made absolute. **Steep look-up** fades the local model + held props out over `HideBodyLookUpFadeSeconds` (1 s) — only when pitch ≤ −35° **and** the pawn is grounded **and** the camera boom trace is squeezed by a ground-like surface (`PlayerMovement.CameraBumpingGround`, hit normal z > 0.5) — and back in when any gate drops (`PlayerAnimation.HideBodyOnSteepLookUp`; owner's screen only — Tint/RenderType are not networked).
13. **Special attack (Q — stab)** — press Q once and the pawn **charges in a frozen windup pose for the class `specialWindupSeconds` (0.3 s oneHanded), then the stab auto-fires** — no hold, no release, never heavy. **The charge IS the windup**: the auto-fired intent carries the charge as hold time, so the host plays zero remaining windup and goes straight into the thrust (the same "windup elapses while held" contract as Attack1); a black stab telegraph shows for the whole charge, and Attack1 presses during it queue as usual (`IsSpecialAttackCharging` is chain-busy). Geometry is `MeleeAttackTypes.Stab` in `MeleeAttackPath` (straight line at side-slash height, pitch aimed 1:1 from the cursor solve, aim stays live until fire), reach = class `reachForwardMeters` **+ `specialReachBonusMeters`**. Cost/damage are the class `special*` fields (`specialActiveSeconds` / `specialStaminaCost` / `specialDamageMultiplier`); same intent → `CombatAuthority` → phased runtime path as Attack1 (`AttackReleaseIntent.IsSpecial`), so block/parry, initiative, outcome recovery, durability and the commitment lock all apply unchanged. A **forward lunge** (`PlayerCombat.SpecialLungeMeters`, default 1 m) fires `SpecialLungeLeadSeconds` (0.2 s) **before the thrust**, owner-driven mid-charge (authoritative on host/offline, predicted on pure clients; the runtime re-applies it authoritatively only for pawns whose owner is remote). The charge **aborts** (never fires) on hit reaction / recovery lock, guard raise, grapple attach, broken weapon, or a stalled tick. Entry gates: melee item equipped (same `PrimaryMelee` gate as the sword), **grounded only**, and **never while grappling** — Q is the grapple detract key (`GrappleAttached` checked owner-side and re-validated on the host, `RejectSpecialUnavailable`). Debug overlay draws **spheres marching outward along the thrust** (the actual sweep volume), not an arc fan; input lives in `PlayerCombat.SpecialAttack.cs`.
14. **Block (hold)** — Attack2 locks teardrop L/R/U on press for HUD / quick attack transition only (**does not** gate block success). While blocking, cover a **front facing arc** (default **270°** = ±135° from look/combat yaw). **Both gates required:** (1) attacker bearing is inside that facing arc; (2) attack ray enters the **body-radius block shell** before the defender body. Block phases: **parry** = block started within `MeleeBlockParryWindowSeconds` (default **0.2 s**); **standard** = holding costs nothing until `StandardBlockFreeSeconds` (default **2 s** from block start); **long** = past that, the host drains `LongBlockStaminaPerSecond` (default **5/s**) and an empty stamina pool breaks the guard (forces re-press). HP/stamina on a landed hit from `Assets/data/melee_block_stagger.json`; recovery poses from combat recovery (not falling stagger).

**Active combat helpers** (do not add parallel systems): `MeleeAttackPath`, `MeleeAttackSweep`, `MeleeAttackResolution`, `MeleeBlockPath`, `MeleeBlockResolution`, `MeleeWeaponClassCatalog` (`Code/Combat/`), `PlayerCombat.ServerMeleeAttack.cs`, `PlayerCombat.Block.cs`, `PlayerCombat.AttackCommitmentLock.cs`, `PlayerCombat.CombatRecovery.cs`, `PlayerCombat.Shove.cs`, `PlayerCombat.SpecialAttack.cs`, `PlayerCombat.Durability.cs`, `AttackCombatTypes.cs`, `MeleeAttackTypes.cs`.

### Artist model import (Rumple's Tripo packs → model + material + prefab)

- **One command per pack**: `Blender/scripts/import_artist_pack.py` (or the `.bat`) takes a single-mesh `.blend` with a packed colour texture and the Pixelate / Posterize node chain and writes `Assets/models/<category>/<name>.fbx + .vmdl` and `Assets/materials/<category>/<name>.png + .vmat`. Categories: `weapons` (import_scale 0.4, hull physics), `building` (0.5 — the kit's 50 u/m, no physics: `BuildPieceCollider` boxes it), `environment` (0.4, mesh physics). Blender metres are game metres; `length=` (weapons) or `scale=` rescale when Tripo's unit-cube normalisation is not the intended size (the sword came out 1.33 m on the diagonal and is imported at `length=1.0`).
- **Texture**: the whole Base Color node chain (Pixelate UV snap, Posterize steps, Hue/Sat, Brightness/Contrast) is evaluated texel for texel in numpy at the Pixelate size (or `texture=N`; weapons use 256) and written as a straight sRGB PNG — verified against Blender's own EEVEE render of the chain (mean error 2/255). `chain=raw` skips the colour nodes and ships the painted texture downsampled: use it when the artist's Posterize wrecks a texture (the sword's brown leather grip became black / red bands at 8 steps, so `sword_reforged` is imported raw; chest and table keep the chain); the `.vmat` uses `shaders/pixel_lit.shader` with `PixelRoughness` taken from the Principled roughness. A Cycles bake was tried first and returns a flat colour for the packed Tripo textures in Blender 5.1, so do not go back to baking. Unknown colour nodes make the script exit with the node name — extend `apply_node`.
- **Frames**: the FBX import turns Blender X into engine Y (the kit's `KitMeshYaw`), so author like the kit and never compensate in the script. Weapons: PCA-straightened, handle along Blender +X with the head at +X (`head=` says which blend axis the tip points along — look at a render), **origin at the butt**; `HeldModelFit` treats an origin within 10 % of one end of the long axis as the butt, so a sword is held by the hilt even though its cross-guard is the wider end (the cross-section heuristic stays for centred models such as the axe). Building: bbox centred on the origin, width X / depth Y / height Z; paste the printed `SizesMeters` line into `BuildModuleDimensions` — that table is the collider and the ground-sit — and set the piece's `fallbackColor` to `1,1,1,1` so `BuildPiece` does not tint the texture. Environment: centred on XY, standing on z = 0.
- **Then the asset**: equipment gets `heldModel` in `equipment_profiles.json` (`club_wood` → `sword_reforged`, `axe_stone` → `axe_reforged`); build pieces get the model on the prefab's `Visual` child at scale 1 with the root `BoxCollider` matching the mesh-frame size (`BuildPieceCollider.Ensure` re-sizes it at runtime anyway), the `SizesMeters` row set to the printed metres and `fallbackColor` `1,1,1,1`. The **chest** is Rumple's `box1pack.blend` since 2026-10-06 (`building chest`, 0.83 × 0.71 × 0.93 m, `models/building/chest.vmdl`; the five testscene1 kit chests were re-seated +10.85 units). The augment station stays a dev box — `augtable1pack.blend` in `Assets/models/building/Blender files/` imports as `building augment_station` (1 × 0.57 × 0.78 m) when wanted. Blend sources stay beside the models (`Assets/models/weapons/blenderfiles/`, `Assets/models/environment/<biome>/blenderFiles/`, `Assets/models/building/Blender files/`).
- **Material-only packs** (`model=none`): when the artist re-saves a pack whose mesh is already in game, bake only the texture + `.vmat`. The clover tree is the case: `clovertree1.blend` is the same 1217-vertex mesh as Rumple's hand-split `clovertree/whole.fbx` (×7.5), so `environment cloverhills/bark model=none` rewrites `materials/environment/cloverHills/trees/cloverTree/bark.png + .vmat` (pixel_lit, 256 texels, his Hue/Sat chain baked in) and every piece of `clovertree_chop.prefab` picks it up through the shared bark material; the cut faces keep `bark_cap.vmat`. The 2026-10-05 axe / sword re-saves only dropped the Pixelate / Posterize chain (same mesh), so they re-import with the same options as before and `chain=raw` is no longer needed for the sword. Packs saved in Texture Paint mode are fine (the script drops to Object mode first). A texture-size comparison variant lives beside it: `clovertree128.blend` (same mesh, a pre-shrunk 128×128 image, no Pixelate node) imports as `environment cloverhills/bark128 model=none` → `bark128.png + .vmat`, and `clovertree/whole128.vmdl` is `whole.vmdl` with the bark remap pointed at `bark128.vmat`; testscene1 has it as the `clovertree_chop_128` prefab instance (ModelRenderer + ModelCollider overridden to `whole128`) 8 m east of the 256 tree.

### Tool / weapon durability + workbench repair

- **Config** lives on equipment profiles (`Assets/data/equipment_profiles.json`): `durabilityMax` (uses before broken; 0 = never wears) and `durabilityDrainSecondsEquipped` (torch/lantern passive drain: 1 tick per N seconds while in the active hotbar slot). Rules live in `ToolDurability`; wear state rides `InventorySlot.Wear` (uses consumed, 0 = fresh) through every grid, cursor drag, container, world drop, and sync RPC. `InventorySlot.CrafterName` rides the same plumbing (set at craft time in `PlayerCrafting.HostTryCraft` for equipment-profile outputs only) — **any new per-item field must be added to every one of those RPC/copy sites together**.
- **Item tooltip** (`PlayerInventoryInteraction.Tooltip.cs`): hover any slot (bag / hotbar / paperdoll / container) for 0.5 s while the menu is open → content-sized popup follows the pointer on the drag layer. Shows name, recipe Type/Description, equipment stats (damage, windup/charge/reach from the item's weapon class row, bow draw, harvest tool, durability, passive drain), food effects from `FoodCatalog`, ammo data, and "Crafted by …" for tagged equipment. `ResourceDefinitionData.Description` is an optional JSON field for raw-resource flavor text.
- **Ticks (host only)**: melee — 1 per swing that connected (hit or blocked), applied in `ServerMeleeAttackRuntime.TrySendCompletion`; bow — 1 per shot fired (`ServerTryFireBow`); build hammer — 1 per place that actually stood (a piece that instantly collapses under structural integrity is free) and 1 per repair (`BuildAuthority`); torch/lantern — passive drain via `EquippedToolDrainAuthority.HostTick` from `CombatAuthority.OnUpdate`, plus per-hit like any melee weapon. **Free swings never cost durability.**
- **Broken (wear ≥ max)**: cannot swing (`CanStartPrimaryAttack` owner-side + `ServerCanBeginMeleeAttackAction` host-side), cannot fire, cannot place/repair structures, and **cannot be equipped** — `PlayerEquipment.TryResolveHotbarEquipResourceId` refuses broken stacks, and since wear changes raise `HotbarChanged`, a tool breaking mid-use auto-unequips (MainHand empties until repaired). Item stays in inventory.
- **Slot visuals** (`ResourceCatalog.ApplyStackVisual`): every durability item shows a thin bottom bar — full tan/yellow when untouched, shrinking with wear, entirely grey when broken — plus a semi-transparent red X overlay while broken. Renders in every grid (bag, hotbar, containers, drag ghost).
- **Repair**: free, at the **workbench** (`Workbench` station, `prefabs/build/workbench.prefab`). E opens the crafting page in workbench mode — recipe list filtered by `CraftingRecipe.AppearsAtStation` (explicit `stations` array; default: `requiredStation` when set, else `workbench`) — with a header button repairing the most-damaged tool (hotbar + bag) to full per click via `PlayerCrafting.HostTryRepairMostDamagedTool`.

### Armor (worn paperdoll pieces)

- **Slots**: `Head / Chest / Arms / Hands / Legs / Feet` are the six armor-set slots; `Cloak` (capes) is a seventh worn slot that contributes armor points and weight but not to the set divisor. `EquipmentSlot` is appended-only — indices ride the equipment RPCs.
- **Data** (`equipment_profiles.json`): `statModifiers.armor` (points), `armorWeight` (`light` / `medium` / `heavy`), `armorSet` (set id, e.g. `leather`), `clothing` (citizen `.clothing` path shown on the pawn while worn). Leather set is three pieces — `armor_leather_head` (Cap, 1 armor), `armor_leather_chest` (Chest, 3 — covers arms + hands), `armor_leather_legs` (Pants, 2 — covers feet) — light, crafted from `crafted_leather` (2 / 10 / 6) at the workbench. A set does not have to fill all six slots.
- **Aggregate** lives on `PlayerEquipment.Armor.cs` (`TotalArmor`, weight-band piece counts, `ArmorSetId` / `ArmorSetPieces`, `HasArmorSetBonus`) and is recomputed **once per paperdoll change**, never per hit or per frame. MainHand is excluded (it mirrors the hotbar, it is not worn).
- **Damage**: `PlayerVitals.ApplyDamageAfterArmor` → `ArmorMitigation.Apply(D, A)`: `D ≤ 0 → 0`; `A ≤ 0 → D`; `A < D/2 → D − A`; else `D² / (4A)`. 100 dmg vs 20 → 80, vs 50 → 50, vs 100 → 25; 20 dmg vs 50 → 2. Applies to every physical hit that reaches `ApplyDamageAfterArmor` (melee, arrows, block chip, animals). World hazards that call `VitalsAuthority.TryApplyDeltas` directly (DoT trap, bear-trap catch) bypass armor. Entities keep their own flat `EntityVitals.ArmorFlat`.
- **Weight → speed** (`PlayerMovement`, Armor group): full-set scales **Light 0.95 / Medium 0.85 / Heavy 0.75**. Each worn piece carries 1/6 of its band's penalty (`ComputeArmorSpeedScale`), so three heavy pieces cost half the heavy penalty. Walk + run are rewritten in the plain-locomotion branch of `ApplyBlockedSprintRunSpeedOverride`; the melee slow and grapple/wingsuit mutes snapshot the scaled values and restore to them.
- **Sets**: `ArmorSetPieceThreshold` (default **3**) on `PlayerEquipment` — reaching it flips `HasArmorSetBonus` and fires `armor_set_equipped` (owner-local, match = set id, rising edge). No bonus effects exist yet; pieces 4–6 are reserved for minor per-piece extras so players can leave augments visible without feeling incomplete.
- **Visuals**: host publishes `PlayerEquipment.NetworkedWornClothing` (`|`-joined clothing paths); `PlayerAnimation.WornClothing.cs` dresses the body via `ClothingContainer.Apply` on every peer and marks the created children `NetworkMode.Never`.
- **UI**: tooltip shows Armor / Weight / Set lines; the paperdoll has a fixed-height `Armor N · Speed NN%` readout under the grid.

### Shelter, comfort, status effects

- **`ShelterProbe`** (`Code/Building/ShelterProbe.cs`) is the global "is there a player-built roof over this spot / is it walled in" answer. Traces filter on the `buildpiece` tag (prefab tag, re-asserted by `BuildPiece`), so caves, terrain and dug holes never count. Roof = structural Roof **or Floor** family above (upper storeys are ceilings); wall = any structural family except Beam. Callers cache: pawns re-probe on `PlayerVitals` **Comfort - Comfort check interval (s)**, static stations on `BuildPiece.WorldVersion` (bumps when a placed piece enters / leaves the world on any machine). Never per frame.
- **Comfort** (`PlayerVitals.Comfort.cs`, host-probed, `[Sync] ComfortLevel` / `ComfortSources`): ticks add up — +1 under a roof, +1 near a lit campfire (`Campfire` **Warmth range (m)**), +1 enclosed (all 8 horizontal probes meet a wall, **Wall hits for enclosure**) **only under a roof**. Fire alone 1, roof + fire 2 (open-concept), roof + walls 2, roof + walls + fire 3. Walls without a roof give nothing. Effects end by time, and systems drop them by event through `HostRemoveStatusEffect` (potions, cures). Each tick banks **Rested minutes per comfort tick** (default 2) on the `rested` effect. The timer **holds at full while comfort is active**; when comfort drops (to any lower level) it counts down from the banked value (10→4 ticks starts at 19:59), and a lower level only holds it once it has fallen to that level's value. Host re-times the expiry only past **Rested top-up slack (s)**; the HUD renders the held value exactly from `ComfortLevel`.
- **Status effects** (`PlayerVitals.StatusEffects.cs`, catalog `Assets/data/status_effects.json` via `StatusEffectCatalog`): timed buffs / debuffs whose modifiers are stat changes — `maxHealthPercent`, `maxStaminaPercent`, `foodDurationPercent`, `healthPerSecond`, `staminaPerSecond`. Host list mirrored through one `[Sync]` string (rewritten only on add / remove / re-time). Pool caps are assembled in **one** place, `PlayerVitals.HostRecalculatePoolMaxes()` = (base + food bonus) × status multipliers; `PlayerFood` no longer sets caps itself, and while rested it pushes the food-duration bonus onto slot expiries in 5 s chunks. Per-second modifiers batch at 0.25 before an authority delta; negative HP goes through `VitalsAuthority.TryApplyDeltas` so death / logging behave like a hit. Death clears every effect (comfort re-applies rested within a check). Console: `status <id> <seconds>`, `status <id> 0`, `status clear` (`GameHacks`).
- **HUD** (`StatusEffectsHud`, built by `PlayerScreenHud.BuildVitals`): fixed-height icon strip **above** the health / stamina bars (bars never move), mm:ss timer per icon, buff = green frame, debuff = red. While any menu is open, the soft cursor over an icon shows a tooltip (name · timer, description, modifier lines, comfort sources). Icons live in `Assets/ui/status/`.
- **Workbench needs a roof**: `Workbench.IsSheltered` (cached on `BuildPiece.WorldVersion`). Exposed bench → prompt reads "Workbench needs a roof", E does nothing, and an open bench closes when its roof is torn down. Host commit check: `PlayerCrafting.HostTryCraft` requires a sheltered bench within **Use range (m)** for bench recipes (not hand-craftable, not campfire-gated); `allCrafting` waives it.

### Doors (swinging leaf on the wall slot)

- **`BuildDoor`** (`Code/Building/BuildDoor.cs`, on `Assets/prefabs/build/build_wood_door.prefab`): the frame (jambs + header) is the piece's static solid — a `ModelCollider` from the frame vmdl (`BuildPieceVisual.UsesMeshCollision` lists doors), so the doorway is a real hole. The old full-module `BoxCollider` filled the doorway in; never put one back. The leaf is authored on the prefab as `DoorHinge` → `DoorLeaf` (leaf vmdl + `BoxCollider`, tag `doorleaf`); `BuildDoor` lays it out once from the model bounds (hinge at one jamb, equal side gaps, sill gap from **`BuildModuleDimensions.DoorOpeningHeightMeters`**) and only ever yaws the hinge.
- **Swing direction is chosen per open**: the host reads the user's position in door-local space and yaws the leaf toward the *other* face (`SwingYawSign`, `[Sync]`). There is no fixed hand — that is what made earlier doors open into the player. `IsOpen` is `[Sync]`; every machine animates the hinge from the synced state (**Door - Swing speed (degrees/s)**, **Door - Open angle (degrees)**), so proxies never fight a networked transform.
- **Leaf collider is keyframed, never `Static`**: a Static body moved every frame does not follow the swing. `BuildNavMeshSync.MarkSolidCollidersStaticInBounds` skips `doorleaf` objects; nav already includes keyframed bodies. Each toggle schedules `BuildNavMeshSync.OnBuildPieceChanged` — closed leaf blocks the mesh (an entity with no route breaches the door like any wood piece; `DamageReceiver` on the root resolves leaf hits through the hierarchy), open leaf lets the path run through.
- **Use**: `PlayerInventoryInteraction.Door.cs` — look + E (`Use`) within **Door - Use reach (m)**, owner trace → host commit (`HostToggle`); a client toggle goes through `RpcHostToggleDoor`, and the host re-checks reach once (`IsWithinUseReach`, reach + one module of slack). HUD prompt reads "Open Door" / "Close Door"; chest / station / workbench focus wins over it. `ShelterProbe` still counts a closed door as a wall (the leaf hit walks up to the `BuildPiece`); an open doorway is a gap, so the room is not enclosed on that ray.

### Foot traps (bear traps)

- **`BearTrap`** (`Code/Environment/BearTrap.cs`) on the hammer-placed pieces `trap_small` ("Foot Trap") and `trap_large` ("Bear Trap") in `data/build_pieces.json` (`Assets/prefabs/build/trap_*.prefab`, sizes in `BuildModuleDimensions`; `BuildPieceNavPolicy` treats `trap_*` as walkable so the plate never carves the nav mesh). The prefab is a thin solid base plus a `Trigger` child (`BoxCollider`, Is Trigger). Armed, the host polls the trigger's `Touching` list at 10 Hz — no per-frame work, no listeners on child colliders.
- **Who it holds**: `TrapSize` (`None` / `Small` / `Large`) per creature, and each trap holds the band **Trap - Smallest creature it holds** … **Trap - Largest creature it holds**. Players are `Small`. Animals read `trapSize` from `data/animal_behaviors.json` (birds / fish `none`, dunewyrm `large`, the rest `small`; a missing key means small). Enemies come from `EntityArchetype` (`Boneback` large, scav / howler small). Small trap = small only; large trap = small **and** large by default (narrow it on the prefab).
- **The hold lives on the movement owner**, never on the trap: `PlayerMovement.HostSetTrapped` (`[Sync] TrapLocked` — no move / jump / roll / grapple, look and swing still work; walk + run are muted like the wingsuit so WASD cannot creep) and `EntityLocomotion.HostSetTrapped` (`IsTrapped` — both brains stop the agent and return early, the body is pulled to the trap centre on catch and held there each fixed step; players are pulled the same way on the owner (XY only, camera untouched); a trapped scav still swings at a target in reach). Players hold **Trap - Player hold (seconds)** (5), animals / enemies **Trap - Animal / enemy hold (seconds)** (10); the pawn also gets the `trapped` debuff for the HUD timer. Death, respawn, or being moved more than 2.5 m releases early.
- **Lifecycle**: **built disarmed** → E to arm → catch → release leaves it **disarmed** again. Look + E (`PlayerInventoryInteraction.Trap.cs`, owner trace → `HostUse`, client via `RpcHostUseTrap` with a one-time host reach check): "Arm Trap" / "Disarm Trap" / "Open Trap" (frees the victim early; the victim cannot open it themselves). Whoever arms it — and anyone already standing on the plate — is ignored until they step off. **Trap - Damage on catch** (default 0) bites through `VitalsAuthority` / `EntityVitals` when set.

### Circuits (wire stripper, nodes, lever → light)

- **Data**: a build piece joins a circuit only when `data/build_pieces.json` says `"circuitEnabled": true` **and** its prefab carries a `CircuitNode` (`Code/Circuits/CircuitNode.cs`: **Circuit - Kind (sphere colour)**, **Circuit - Sphere offset (units)**) plus one `ICircuitDevice` component (`CircuitLever`, `CircuitLight`, …). First pieces: `circuit_light` ("Light Bulb", 0.3 m cube, `CircuitLight`) and `circuit_lever` ("Lever", 0.2 × 0.2 × 0.3 m, `CircuitLever`); sizes in `BuildModuleDimensions`, `BuildPieceNavPolicy` keeps every `circuit_*` piece off the nav mesh. Gates will be 0.15 m cubes.
- **Wires are invisible and two-way**: a wire is stored on one of its ends (the source end when there is one) as one `[Sync]` string (`CircuitLink.Encode`, `guid:cable;…`), so every machine draws the same graph and late joiners get it for free, but power travels both directions along it — direction of the drag never matters. Cable colour (red / blue / green, `CircuitCable`) is a label only — every wire carries the same signal.
- **Solve** (`CircuitRegistry`, host, event-driven): the wire graph is undirected; each connected group of nodes is **one circuit**, live when **any** source in it is on (two levers on one circuit = OR; it is only off when every lever is off). Every node's `Powered` is its circuit's state; its device turns that into `Output` (`ICircuitDevice.ComputeOutput`: lever returns `IsOn`, light mirrors `Powered`). Anything that changes the graph calls `MarkDirty`; the next host frame floods each circuit once. No per-frame work while quiet. Both `Powered` / `Output` are `[Sync]`; devices read them for visuals on every machine.
- **Wire stripper** (`tool_wireStripper`, `EquippedItemActions.Wire`, `Code/Player/ToolWireStripper.cs`, prefab `prefabs/tools/wire_stripper_tool.prefab`): with it out, `CircuitWireOverlay` draws a 0.3 m sphere (`CircuitNode.SphereDiameterMeters`) in each circuit-enabled object within **Wiring - Show range (m)** (kind colour: switch yellow, light blue, door teal, trap red, gate lime, sensor purple, power white), 10% bigger under the crosshair, plus a line per wire in its cable colour. Hold Attack1 on a sphere, walk, release on another → `PlayerInventoryInteraction.Circuits.cs` sends intent, host validates once in `CircuitRegistry.HostToggleLink` (both circuit-enabled, not self, under 50 m, pawn within **Wiring - Reach (m)** of the released sphere) and lays the wire — or removes it if that pair was already wired. A wire dragged from a sink to a source (bulb → lever) is flipped onto the source, so drag direction only matters between two non-sources. Sphere picking is a ray-to-centre test against cached positions, no trace. Attack2 opens the cable colour menu (`Code/UI/Circuits/WireCableMenuHud.cs`, same overlay pattern as the build menu).
- **Lever**: look + E (`PlayerInventoryInteraction.Lever.cs`, owner trace → `HostToggle`, client via `RpcHostToggleLever` with a one-time host reach check); prompt "Switch On" / "Switch Off". **Light**: `CircuitLight` tints the bulb and switches a `PointLight` it builds once from **Light - Light color** / **Light - Light radius (m)**.
- Not yet: generator / power model, gates, timers, sensors, buttons, pressure plates, doors and traps as sinks — pending Mark's answers on colour meaning, power model, pins, and hand-opening a wired door.

### Build structural integrity (Valheim model, Valheim numbers)

- **Model** (`BuildStructuralIntegrity`, host-only, event-driven from `BuildAuthority` — never per frame): each placed piece holds one support value = the best any *touching* neighbor can pass it, decayed by `S_child = min(childMax, S_parent × (1 − L(θ) × 2.1))` — a **fixed one-module hop per connection**: support is budgeted in pieces, not meters travelled (per Mark: stacked thin beams max out at the same count as stacked walls). `L(θ)` lerps horizontal→vertical loss by the connection's upness (hanging = horizontal). No accumulated weight. Grounded pieces (short down-probes from the lowest oriented corners hitting static non-build colliders — terrain, rocks, trees) seed at material max.
- **Materials** live in `Assets/data/build_pieces.json` → top-level `materials` array; pieces opt in via `materialId`. Wood = Valheim wood exactly: max 100, min 10, vLoss 0.125, hLoss 0.2 → exactly 8 pieces straight up (any sizes), grounded piece + 4 out sideways. **No materialId = exempt** (chest, workbench, augment station, campfire, repair) — deliberate, do not add one to furniture.
- **Collapse**: placement is never blocked — a piece below its material minimum places, then the solver destroys it (place-then-collapse, per Mark). Demolishing re-solves the touched component (the removed piece is explicitly excluded — engine destroys are deferred, so it would otherwise keep "supporting" its structure that frame). Support below min never props others, so one Dijkstra pass lands on the post-cascade state; the doomed set is then destroyed **bottom-up, one piece per 0.12 s wave** by `BuildCollapseRunner` (first piece pops synchronously so a place-then-collapse still refunds the hammer swing). Each queued piece is re-checked at its wave — rebuilding support mid-collapse rescues whatever still solves above min.
- **Feedback**: hammer-out hover tints the aimed piece via the support gradient (blue max → red near min) and `BuildSupportReadoutHud` shows "Support N%" under the crosshair (numeric on purpose — not color-only). Values reach clients through `[Sync] BuildPiece.Support`.

### Entity AI perception + biome population

- **Perception / AI states**: alert → chase live player + attack until geometric LOS lost for **30s** (`ChaseLosLostAbandonSeconds`). No flank/break/last-known hunt paths. Nav uses live **PhysicsWorld** via `GenerateTiles` when structures change; the coalesced local rebake queue is ticked by `BuildNavBakeSystem` (a `GameObjectSystem`, every scene) — it used to hang off `TerrainWorldManager`, so scenes without streamed terrain never rebaked around placed walls and agents walked through them.
- **Path validation follows the ground** (`EntityBrain.PathCrossesSolid`): each nav segment is re-grounded every 96 u with a down probe before the body-height sweep, and `PathCrossesSolidCached` reuses the verdict for 1.5 s while the path's endpoints and length are unchanged (invalidated on every bake) — a dozen entities re-validating every 0.3 s was the other half of the renav lag. A string-pulled path has no point where a stair meets a floor, so the raw stair-foot→floor segment sliced through the slab from underneath and vetoed every route up a structure (`blocked … status=Complete crossesSolid=True` on every line of the log) — the entity breached instead of climbing, and the route through a hole it had just opened was vetoed the same way.
- **Stairs / roofs are routes, never walls** (`BuildPieceNavPolicy.IsWalkablePathObject`): the movement clip, wall-steer, `PathCrossesSolid` and the breach in-the-way probe all skip WalkablePath pieces — a stair riser or a roof edge is a vertical face and every normal test read it as a wall, which is why scavs breached stairs instead of climbing them. Feet-glue follows build-piece height at 600 u/s (terrain keeps its 55 u/s ease) so a 45° roof can be run up at 220 u/s without sinking into the slab. Runtime nav limits: max slope 55° (scene 40°), step 40 u (scene 18).
- **Chase goal is where the player stands**: `GetLiveChasePoint` asks `EntityNavMeshUtility.TryFindNavAtFeet` (tight box sample around the feet, ±40 u xy / ±48 u z — deterministic, never the ground a storey below) for nav under the player (terrain or a build floor / roof at any height) and paths there. Only an airborne / grappling player falls back to "the ground under their XY". Melee needs the target within `MeleeVerticalReach` (64 u) — an entity never enters Attacking against someone a floor above.

### Structure breaching (entities vs build pieces)

- **Pieces have hit points**: `materials[].health` in `Assets/data/build_pieces.json` (wood 100) → `[Sync] BuildPiece.Health`, seeded on the host at placement / start. Furniture without a `materialId` has none. **Only entities damage structures** — `CombatAuthority.MayApplyMeleeDamageFromAttackerToReceiver` refuses build pieces for attackers without an `EntityBrain`, so a player's sword on a wall is not a hit (no swing consumed, no durability); players use the hammer. Every destructible build prefab carries a `DamageReceiver` (authored on the asset); `DamageReceiver.TakeDamage` routes to `BuildPiece.HostApplyDamage`, and at 0 HP the piece leaves through `BuildAuthority.HostRemovePiece` — the same nav rebake + structural re-solve as a hammer demolish, so knocking out a load-bearing piece collapses what it held. Hammer hover readout shows `HP x / max` next to support.
- **`EnemyAiState.Breaching`** (`EntityBrain.Breach.cs`): entered from Chasing the moment a **fresh** mesh has no complete route to where the player stands (goal off nav, path missing / partial, or through a solid — `StartNotFound` is our own footing and does not count), after `BreachAfterBlockedSeconds` (0.3 s). A wedged fallback (complete route, body not moved for `ChaseWedgedSeconds`) remains. The 72 u body-height in-the-way probe (`RememberPieceInWay`) only remembers a piece ahead as the preferred target; the same probe while walking to a breach stand retargets onto whatever blocks the walk. Then it walks to a stand beside the piece (nav-projected probe off each horizontal face, must be inside `StructureAttackRange` = 60 u of the surface with a complete path) and hits it **until it is dead**. `EntityLocomotion.ClipMovementAgainstSolids` keeps the body sphere a full radius off any wall and treats a started-solid sweep as blocked — a flush start returned a zero normal that read as "nothing to slide on", which was how entities tunnelled through walls. Breach decisions log as `[Breach] <entity>: …`, piece damage as `[BuildPiece] …`, executed rebakes as `[BuildNav] …` (read `sbox/logs/sbox-dev.log`). Then it walks to a stand point beside a piece (nav-projected probe off each horizontal face, must still be inside `StructureAttackRange` = 60 u of the surface with a *complete* path), hits it `BreachSwingsPerPiece` = **3** times (counted on `EntityCombat.AttackCycleFinished`), marks it recently-hit (20 s) and moves to the next piece — so a whole building comes down over time. All candidates hit → next lap over the same pieces.
- **Plain nav only** (Mark, 2026-09-09): the mesh is correct, so pathing finds doors and stairs by itself. The two-leg detour search and the drop-in (walk above the player and jump down) were removed with their files — they produced the "runs off, turns round, comes back" whenever the mesh was stale. **Breach trigger is immediate**: on a fresh mesh, no complete route to where the player stands (goal off nav, path missing / partial, or through a solid) → pick a piece after `BreachAfterBlockedSeconds` (0.3 s, absorbs one bad query). A wedged fallback (complete route but the body has not moved for `ChaseWedgedSeconds`) remains. **Stay on the piece until it is dead**; wood `health` is 30 so a piece dies in three scav hits (10 each) — "3 hits" is material health, not a swing counter.
- **Baked tiles never saw the buildings**: nav tiles cache a heightfield, and in a scene that loads baked navdata (testscene1) that cache comes from the bake, not live geometry (`NavMeshTile.IsBakedHeightField`). A plain `GenerateTiles` rebuilt tiles from that cache, so placed walls never carved and upper floors never got a mesh (`nav_probe` on a floor at z≈102: "nav at feet NO" while nav bounds reached z 40000). A full `Generate(physics)` does rasterise the buildings (`nav_regen` → "nav at feet YES"); incremental `GenerateTiles` never carved a fresh wall in this scene even after every tile was live (36 "path leaks through a solid" after the load-time generate). Hand-built scenes also get a **nav bubble** (Mark): the load-time pass waits up to 15 s for a player pawn, then sets custom bounds ±6000 u (150 m) around it — the scene's whole-world bounds (1 km²) made every structure regenerate ~5 s. Beyond the bubble there is no nav in a test scene. - **Piece choice** (per Mark): candidates are only pieces that relate to the **player** — on the eye→player line (what they are behind), the piece the entity is pushing against on the way to them (`NotifyChasePhysicsBlocked`, 3 s memory, and only if it is closer to the player than the entity is), or **part of the structure the player stands on** (`FindPieceUnder` → `BuildStructuralIntegrity.GetConnectedPieces`, the solver's touching-neighbour closure; event-driven, once per pick); the `BreachSearchRadius` (400 u) rule only applies when the player is on the ground. An unconnected structure beside the one they stand on is never a target. Never a piece that is merely near the entity: the other half of a split base, or the house next to the tree the player grappled into, gets no swings. Score = flat distance **from the player** − 3 × Support ("what is holding up the weight"); when the player is above melee reach, pieces under their feet within 150 u come first (the supports of what they stand on). No candidate → no breach, the chase carries on. The chosen piece is re-tested every recheck (`IsPieceStillRelevant`): the moment the player moves to another structure it re-picks at once rather than finishing the wall. ### Vehicles (dune buggy)

- **`Vehicle`** (`Code/Vehicles/Vehicle.cs` + `.Physics` / `.Seats` / `.Fuel` / `.Health` partials) on `Assets/prefabs/build/vehicle_dune_buggy.prefab`: a host-spawned networked `Rigidbody` placed with the build hammer (`"vehicle": true` on `vehicle_dune_buggy` in `build_pieces.json`, size in `BuildModuleDimensions.SizesMeters`). It is **not** a `BuildPiece`: `BuildAuthority.HostPlacePiece` returns right after `HostNetworkSpawn` for vehicle data, `BuildPieceCollider.Ensure` leaves prefabs with a `Vehicle` alone, the nav baker skips the `vehicle` tag, no structural solve. Every drive / steer / suspension / fuel / health number is a property on the prefab's Vehicle component (meters, m/s, m/s², Hz); the prefab bakes them, so changing a code default does nothing until the prefab is re-saved.
- **Physics** (`Vehicle.Physics.cs`): four raycast springs from the wheel mounts (spring + damper from `SuspensionFrequencyHz` / `SuspensionDampingRatio` and the chassis mass); a ray that starts inside the ground or meets a surface facing away from the chassis (normal · up < 0.35 — a buggy lying on its side) is not a grounded wheel (counting it used to fire full compression and shove the chassis upright). **Tyres use GTA V's traction curve** (Mark 2026-10-21: "feel like GTA 5"; field meanings from Eddlm's 5mods handling.meta guide): grip rises with slip angle (sine) to `TyreGripCoefficient` (fTractionCurveMax, μ 0.9) at `TyrePeakSlipDegrees` (fTractionCurveLateral — 10°; GTA's usual 22.5 is too soft on this model, the body swings out before it bites), then falls linearly to `TyreSlideGripCoefficient` (fTractionCurveMin, 0.75) over the same angle again; `TyreGripBiasFront` (fTractionBiasFront, 0.48) scales front × 2·bias, rear × 2·(1−bias) so the tail stays planted. The side force is that grip × the wheel's own spring load (never more than would cancel the slip in one step), and the friction circle is **side-first**: drive / brake get only the grip the corner leaves over — an even split let throttle steal the rear's side grip and spin it out in a planar sim. Before this the side force tried to cancel all slip in one step, which saturated every tyre in any real turn, squeezed the drive force to nothing (W + A topped out at ~27 mph) and let the rear drift. Forces are applied at the **ground contact** with `Rigidbody.ApplyForceAt` (Mark 2026-10-04: rollover must come out of the physics, not a scripted roll). A hard turn loads the outside wheels and unloads the inside ones; whether it slides, tips onto two wheels or rolls over its cage falls out of speed, steering angle, slope, bumps, the Rigidbody's mass centre (z +2 u) and the track. Rigidbody angular damping is 0.3 (was 1.5, which soaked up every roll). **Rollover is entirely physics** (Mark 2026-10-21: "flipping was a hard set mechanic … if you take a sharp turn and hit a bump at the same time the dune buggy can roll over"): the 2026-10-06 lateral-g capped lock (`SteerLockDegreesAtSpeed`, `SteerLateralLimitG` / `…TopSpeedG` / `…Curve`) decided the roll speed by script and is deleted — steering is now GTA's speed-limited lock done as a **slip limit**, not a lateral-g target: `ApplySteerSlipAssist` lets the front wheels turn at most `SteerSlipAssistFraction` (0.8) × `TyrePeakSlipDegrees` past the direction the front axle is travelling, so the fronts sit just under peak grip at any speed (full `MaxSteerDegrees` 26 below ~2–6 m/s and in reverse), ramped at `SteerSpeedDegreesPerSecond` (110). It never asks for more than peak grip, so whether the buggy rolls is still tyre grip vs. the tip point plus whatever the ground adds. Planar sim (no load transfer): W + A from rest climbs to the 54 m/s cap on a widening line with the tail ~6° out. The airborne angular-damping swap and self-right torque (`AirborneAngularDamping`, `AirborneUprightStrength`) are deleted too: in the air the chassis keeps the spin it earned, under the Rigidbody's own 0.3 damping. What decides a roll now is **tyre grip against the tip point**: static tip ≈ half-track ÷ mass-centre height ≈ 1.19 m ÷ 1.10 m ≈ 1.08 g (≈1.04 g with body roll). The prefab's `TyreGripCoefficient` is **0.9** (was 1.3, which rolled any flat full-lock turn above ~20 mph without the cap), so a flat hard turn slides or rides on three wheels; a bump, kerb or slope during the turn adds the roll that trips it. Raise μ toward ~1.05 to roll more easily, lower it to make it slidier and harder to trip. The bump stop (`SuspensionBumpStopMultiple` 3 × static wheel load) stays: it is a spring limit, not a roll rule, and stops a fully compressed landing launching the chassis. `vehicle_rolltest` holds its entry speed through the turn (wide open it reached 37 mph on a "25 mph" run). Earlier (2026-10-04, mass centre +2, μ 1.2, 32° linear): 30 / 45 mph slid flat, 60 rolled. **Collider**: the root `ModelCollider` uses `dune_buggy.vmdl`'s own physics hull — one convex `SingleHull` of the body mesh (cage, nose, rear, A-arms; friction 0.8) — so the hoop can't sink into the ground and the buggy can rest on its side or roof; the old 168×90×34 box only covered the floor pan. **W** drives up to `MaxSpeedMetersPerSecond` (54 ≈ 120 mph; doubled from 27 on 2026-10-04, Mark: too slow); **S** brakes while rolling forward and only reverses once stopped (`ReverseSpeedMetersPerSecond` 7); W does the mirror when rolling backwards (Mark: wheels never spin against momentum). No pedal / on the limiter → `RollingDragMetersPerSecond2`; tank empty → the engine is dead, W does nothing and the buggy coasts down at `OutOfFuelCoastDragMetersPerSecond2` (1.5, ~35 s from the cap; S still brakes) — Mark 2026-10-04. Steering lock is the slip-limited `ApplySteerSlipAssist` (see Rollover). Measured 2026-10-02: 0–60 in ~4 s, 60→0 in ~2.5 s, a left turn of 150° in 3 s with the chassis level. Host sets `[Sync] ActiveSeed` (`Seed` property, 0 = random each start); every peer builds identical geometry locally from that seed (`DungeonLayout.Generate` is pure — no engine types), so nothing but the chests is networked. Chests (dead ends) go through `BuildAuthority.HostPlacePiece( "chest" )` on the host and are filled with `ContainerInventory.HostDepositStack` from a small loot table, so they open / network like any hammer-placed chest.
- **Layout** (`DungeonLayout`): a cell grid per floor (`Width × Depth`, pitch **Cell pitch (m)** 16 m). Rooms occupy **footprints** of 1×1, 2×1, 2×2, 3×2 or 3×3 cells (`CellsW × CellsH`, interior = base 9 / 12 m + one pitch per extra cell, so a 2×2 is 28 m across and a 3×3 is 44 m) and are `Rect` or `Round` (1×1 → 6 m radius, 2×2 → 14 m). **No small rooms** (Mark: 6 m pockets were useless) — the smallest is 9 m. A growing-tree walk from the entrance cell (west edge, middle row) steps out of a free perimeter *slot* (cell-side) of an open room; a step lays a straight **corridor run** of 1–**Longest corridor run** cells with **Corridor chance** (a `Corridor` cell is a 2.5 m square with no wall on its open sides; later steps out of any corridor cell give bends and T-junctions), then a room at the end — **Big room chance** tries a multi-cell footprint first and shrinks until one fits, **Round room chance** picks the shape. Every multi-cell room is a **hub**: it immediately grows 3–6 branches so it ends up with many doors (Mark: "6 doors off it"); otherwise room picking is weighted by perimeter, so big rooms branch more. `Winding bias` picks between continuing from the newest room (long paths) and a weighted random open room. Doors are per perimeter cell-side (`DungeonDoor`: side + cell), so a wide wall can hold several. Floors link only through **stair rooms**: after a floor is grown, the deepest eligible single-cell room (≤2 doors, ≥2 free cells beside it upstairs) plus random deeper-half picks become `StairUp` (forced 12 m rect, a door-free wall side becomes `StairSide`, preferring one whose upstairs neighbour is already blocked) and a `Landing` is created directly above (same cell, same side blocked for doors — a door there would open onto the stairwell hole); the landings seed the next floor's growth, so the whole dungeon stays one tree. After each floor, `PruneDeadEnds` removes corridor stubs (one door) and landings that never grew a door (their stair room reverts), then re-indexes. Dead ends (one door, not entrance / stairs / corridor): the deepest always gets a chest (`Treasure`), the rest by **Chest chance per dead end**. Pillars: big rects draw Grid / Colonnade / Square / Ring, 12 m rects Center / Square / Corners / Row / Ring, 9 m rects Center / Square, round rooms Center / Ring; stair rooms and landings only Center or none (the strip along the stair wall must stay clear); corridors and the entrance none.
- **Geometry** (`DungeonGeometry`, all sizes converted once from the component's meter properties): dev boxes (`models/dev/box.vmdl` + `materials/default.vmat` tint, 50 u cube scaled, optionally yawed) with static `BoxCollider`s, one `Floor_N` child per floor (`dungeon_floors <n|all>` hides floors above n locally — upper plates cover lower rooms, there is no roof otherwise). Colours cycle by **room depth** (`ColorDepth`: corridor cells inherit their parent's, so a long hallway stays one colour) through a 10-hue palette (walls ×0.7, pillars ×0.45, halls the average of both ends, treasure floors gold), so walking back cycles the palette backwards. Rect walls are 0.4 m outside the interior (N/S walls cover the corners, E/W stop short — no overlapping volumes), split around every doorway on that side (hallway-width, 2.5 m, lintel from **Doorway height** up; corridor cells get no lintel and only their N/S corner posts remain). Round rooms: the floor is axis-aligned strips inscribed in the outer wall circle (there is no dev cylinder), the wall a ring of ~1 m rotated segments skipping the doorway's angular span, with a chord lintel over each gap. Halls run from wall face to wall face between the two door cells (`FaceDistance`: rect = half extent + wall from the cell centre; round = the ring point at the doorway's outer edge, and hall walls bury their ends one wall thickness into the ring); **hall plates sit 1 u below room plates** so tops never z-fight. Stairs: `StepCount = FloorHeight / StepRise` (4 m / 0.4 m = 10 steps of 0.7 m run) as solid blocks hugging `StairSide` from one corner; the landing plate is the full plate minus that exact footprint (four strips), so the last tread meets the plate flush and there is head-room from step 5 up. Ground plane top sits at z = -2 so floor-0 plates (top at 0) never z-fight it.
- **Map reveal** (Mark, 2026-09-24 — the map page maps rooms as you go, one floor layer at a time, stairs clearly marked): `DungeonMapModel` (built with the geometry from the same layout + params, everything in world meters: room centre / half extents / round flag, per-door centre + orientation, hall interior rects, stair-run / stairwell footprints, the entrance doorway) and `DungeonExploration` (client-local, per session: visited room + hall indices, `CurrentFloor`, `Version`; reset to "entrance only" on every rebuild). The generator samples the local input-owned pawn (fly camera when there is none) every 0.25 s: floor = `floor((z + 0.35·FloorHeight) / FloorHeight)` so the layer flips a third of the way up the stairs; the cell under the viewer marks that room (corridor cells count); halls are marked when stood in or once both end rooms are known. `TerrainWorldMapFace` has a `_dungeonLayer` (z 0, under strokes) rebuilt only when the (map, version, floor) key or the zoom geometry changes: **only the current floor's discovered rooms and halls are drawn** — interior rect (round rooms `border-radius: 50%`) grown by the wall thickness with the wall as its border in the room's cycle colour (treasure gold, halls the blend), doorways as opaque floor-coloured tabs across the wall band (so exits show as gaps), stair runs / stairwell holes as white pads with a constant-size **UP** / **DOWN** badge, **IN** at the entrance doorway. The minimap shares the face, so it shows the same reveal. `MapMenuSection` adds one fixed line under Controls — "Dungeon: floor 2/3 · rooms 5/38" (`BoxDungeonGenerator.Active`, `RoomCount` / `VisitedRoomCount` exclude corridor cells). Nothing is persisted or networked: each player's map is their own, like pins.
- Console: `dungeon_regen [seed]` (host; remotes rebuild when the synced seed changes), `dungeon_floors <n|all>`, `dungeon_info` (per-floor rooms / stairs / chests / deepest depth). Player: `L` (`TerrainTestPlayerSpawn` on the same object) spawns the playable pawn at the fly camera, which starts just outside the entrance.

### Procedural cave (caveVertTest scene)

- **`CaveDungeonGenerator`** (`Code/Dungeon/`, on the `Cave` object in `Assets/scenes/caveVertTest.scene`): the object's transform is the rim of the first drop. Same networking contract as the box dungeon — host sets `[Sync] ActiveSeed` (`Seed`, 0 = random), every peer builds identical geometry locally from `CaveLayout.Generate` (pure, meters, no engine calls — it compiles and runs under plain .NET with a `Vector3` shim, which is how it is verified), and only the chests are networked (`BuildAuthority.HostPlacePiece( "chest" )` + `HostDepositStack` loot). `TerrainTestPlayerSpawn` sits on the same object; the fly cam starts on the platform, `L` spawns the pawn with the grapple.
- **Shape: one long descent, mainly one path, almost no flat ground** (Mark: no central tube everything shoots off from; "mainly just one path, not so many offshoots"; horizontal areas "very rare"). The **trunk** (`Passages[0]`, `CavePassage.Kind == Trunk`) is one swept tube of 45 m **drop** sub-legs that drift, walk their radius (pinches down to **Narrowest radius (m)** 3, caverns that swell to 22–36 m over four sub-legs, never faster than 0.4 m of radius per metre of height so the wall stays within hop reach) and now and then become a **chute** — a steep leaning run (20–36 m sideways per 45 m) that carries the shaft sideways and turns its heading; that is how the cave wanders without ever going flat. Flat floors exist only where they are needed: a 10–16 m **landing** under a **chimney** (climb 40–150 m, leaning 20–40 m away from the drop it follows) and a 10–14 m landing on its apex, a rare **tunnel** (4–10 % per drop by archetype, sometimes a cavern), the one **junction hall** (25–40 m, **Junction halls** 1) where branches fork, and the **chamber** (**Chamber radius (m)** 40) at **Net depth (m)** 3000. Every straight run is checked against the polyline so far (skipping only the run it continues, or the apex + chimney for the drop after a chimney, which also chutes away slim for three sub-legs) so the chain never crosses itself. Five archetypes (`Shaft`, `Stairs`, `Serpent`, `Chimneys`, `Caverns`; **Archetype** −1 = from seed) set drop lengths, drift, chute and pinch chances, bulges, climbs and turn angles. Over 40 seeds: trunk 3.2–4 km, route 4–7.8 km, ~3.5 chimneys and ~2 side rooms per cave, spread 180–740 m.
- **Sweep** (`CaveLayout.Trunk.cs`): straight legs with corners rounded to ≈ 1.4 × tube radius, rings every **Trunk ring spacing (m)** 4 m / **Passage ring spacing (m)** 2.5 m, **parallel-transported frames** (continuous, so rings never twist; anything that needs "up" or "sideways" in a ring asks `UpAngle` / `SideOf` / `AngleAtHeight`), a per-leg radius profile (`R0 → R1` with an `RPeak` bulge), and a flat **floor** in walk legs that also reaches 1.6 radii into the neighbouring drop / chimney, so every shaft bottom is a flat floor; walk legs inherit the previous floor (a hall's far end is lowered to where the next tube keeps the same floor). `TubePoint( passage, ring, φ )` is the one rock-surface function (radius + `TubeNoise` + floor clamp + pond bowls) that the mesh, the mouths and the ledges all read.
- **Mouths** (`CaveMouth`, always on the trunk): hole patches in the trunk's ring × segment grid. `MakeMouthVertical` cuts a drop wall around a world direction (the whole hole sits under the previous ledge; the floor is the bottom edge's highest vertex); `MakeMouthSide` cuts a landing / hall side wall from one segment under the floor up to two throats above it (through `AngleAtHeight`, so it works whatever the frame roll). Mouths never overlap each other.
- **Branches** (`CaveLayout.Passages.cs`), deliberately few: **Dead-end rooms off the drops** 2 hang off route hops (doorstep under the mouth, validated as a real hop: lower, within grapple reach); the junction hall gets **Decoy rooms per junction** 1–2 dead-end mouths on its side walls and, if **Loops** > 0, a loop that rejoins the trunk through an exit mouth on a later walk leg (rare in practice, since walk legs are short). A dead end is walk out 15–30 m → 35 % a chimney up 15–40 m / 20 % a drop 10–30 m / else straight → a room of radius 10–25 m and length 2.5–4 × radius, domed shut; chest at the far end, a light, and with **Pond chance in a big room** an oasis pond when the radius ≥ 12 m. `PassageClear` rejects a tube that breaks the platform or touches any other passage; `DebugLog` keeps rejection reasons.
- **Route** (`CaveRoutePoint` list, `CaveLayout.Route.cs`): rim → down each drop group (`DescendTube` on a `LegTube` over the group's near-vertical samples, starting at the wall nearest the previous route point — from a floor the route first walks to that edge) → landing / junction (branches built here) → up each chimney (`AscendTube`, grapple hops rise 5–10 m) → … → chamber. Steppers solve the tangential step against the real horizontal distance, promote jump hops to grapple hops when the wall flares or drifts, allow the tube's own **lean** between two heights as free sideways distance, swing across pinches only where the tube is vertical, and instead of endless retries go straight down the same wall once the start would exceed the grapple drop limit. Ledge kinds (`Slab`, `Jut` tilted and rolled, `Shelf`, `Spur`, `Boulder` rolled ±15°, `Doorstep`) by weight, protrusion ≤ 45 % of the local radius. Fillers (**Filler ledges** fraction) go on the drops. `RoutePathMeters` / `RouteClimbMeters` / `RouteDescentMeters` are measured after generation.
- **Chamber + oases**: the chamber is the final walk leg; its pond is a `CaveBowl` against one wall with the waterfall crack above it (`AngleAtHeight` on the wall, 16–24 m up), the chest on the bank. Every bowl (chamber, junction hall with **Pond chance in a junction hall**, big rooms) gets `BuildOasis`: the water rig (`water`-tagged trigger + `WaterVolume` + translucent body + `tempwater.vmat` surface), slate paths stepping into the water, boulders, moss, reeds, a teal light. The waterfall stays a placeholder until there is a particle / shader waterfall.
- **Geometry** (`CaveGeometry` + `.Dressing`): one runtime `ModelBuilder` model — every passage as rings of **Trunk segments around** 48 / **Passage segments around** 28 vertices from `TubePoint`, the trunk first with its mouth holes skipped, each branch's entry ring **zipped** onto its hole loop (both walked by polar angle in the mouth frame) and its last ring zipped onto the exit mouth or domed shut, the trunk's first ring fanned out to the square **entrance platform** and its last ring domed (the chamber's far wall); `AddCollisionMesh` + `AddTraceMesh` → `ModelRenderer` + static `ModelCollider`, tags `solid` / `dungeon`, **no `grapple` tag**. Ledges are dev boxes grown from `AnchorMeters` along `IntoVoid`, buried 3 m + noise into the rock, with `BoxCollider`s and the **`grapple` tag** — the only hookable surfaces. Debug tint: jump hops gold, grapple hops blue, climb hops green, fillers grey, doorsteps pale.
- **Verification**: the session scratchpad `Harness` (net7 console app compiling the four `CaveLayout*.cs` files against a `Vector3` shim) generates N seeds, checks every hop against the limits (lean-aware on the trunk), tube-vs-tube clearance (the trunk against itself too), ledges-in-mouths and frame orthogonality, and renders X-Z / Y-Z side views as PNGs at 1 px = 2 m. Rebuild it whenever the layout changes, and look at the renders — the numbers alone did not catch the "central tube" problem.
- Console: `cave_regen [seed]` (host), `cave_info` (trunk legs with their branches, passages, every route point with gap / dz / kind), `cave_tp <routeIndex|top|bottom>`, `cave_tp room <n>`, `cave_tp junction <n>` (local pawn).

## Commandment #4 — Meters are the design language; convert once, at the read site

**Designer-facing values are written in meters.** A property named `…Meters` holds exactly the number the user said: 100 m → **100**. Never pre-scale that number in the property, in JSON, or in a scene transform you type by hand.

**The world is not 1:1.** s&box inherits Source units, and this project has two conversion factors:

| Space | Factor | Converter |
|-------|--------|-----------|
| Terrain, environment, sky, fly-cam, harvest, containers, grapple | **40 u/m** | `TerrainWorldUnits.MetersToEngine` |
| Pawn distances (shove dash, bow range, wingsuit) | **≈40 u/m** | `BodyHeight / 1.8` — Citizen `BodyHeight` 72 ≈ 1.8 m |
| Build pieces only — snap math and piece colliders | **50 u/m** | `BuildColliderSnap.PrefabColliderSize` |

Convert **once**, inside the system that owns the value, and never carry a converted number across a system boundary. A value that has already been converted (a mesh AABB, a `BuildPieceModelCache` extent) is in final world units — do not scale it again.

| User says | Property value | What the read site produces |
|-----------|----------------|------------------------------|
| 1500 m star shell | `ShellRadiusMeters` = **1500** | 60,000 units via `MetersToEngine` |
| 1 m shove dash | `ShoveDashMeters` = **1** | ≈40 units via `BodyHeight / 1.8` |
| 2 m wall module | `ModuleMeters` = **2** | 100 units via `PrefabColliderSize` |

**Open item:** build's 50 u/m is the odd one out. Unifying it to 40 would move every snap point in the kit, so it stays until that migration is done deliberately.

Enforced via **`.cursor/rules/meters-are-engine-units.mdc`**.

## Commandment #5 — No Ensure* bandage components

When a prefab or scene object is missing what it needs, **fix the asset**. Do **not** add a runtime helper (`EnsureChopableTrees`, `AutoWire*`, folder bootstraps that `Components.Create` on children, etc.) to paper over incomplete setup.

- Prefer clarifying requirements and s&box prefab/instance behavior over guessing.
- Author `ChopableTree` + `DamageReceiver` (and similar) on the tree prefab or scene instance.
- Repair bad prefab instance patches (`RemovedObjects`) instead of compensating in code.

Enforced via **`.cursor/rules/no-ensure-bandage-components.mdc`**.
